# 02. 要求（What / Why）

[READMEへ戻る](../README.md) · 前：[01. ユーザー課題](01_user_problem.md) · 次：[03. 要件](03_system_requirements.md)

課題ごとに「何ができればよいか（What）」と「なぜ必要か（Why）」をまとめます。どう実現するか、どこまでできればよいかの条件は、[03. 要件](03_system_requirements.md)に分けています。

## 課題から要求へ

| 課題 | 要求（What） | 理由（Why） |
| --- | --- | --- |
| 作業中に分からないことを、すぐ確かめられない | 作業員が、その場で映像と言葉を使って質問できること | 作業を止める時間を短くし、状況を正しく伝えるため |
| 教材から必要な場面を探せない | 必要な場面（動画の区間）へ、すぐたどり着けること | 動画を最初から見直す時間をなくすため |
| AIが根拠なく答えると危険 | AIは承認済みの根拠があるときだけ答え、なければ人へつなぐこと | 誤った手順や判断による事故・不良を防ぐため |
| 回答がその場限りで終わる | ベテランの回答が、承認を経て次の質問の根拠として再利用されること | 同じ説明の繰り返しを減らし、知識を組織に残すため |
| 共用端末を複数人で使う | 共用端末でも、重要な操作は本人が確かめられ、記録が残ること | 承認や停止の責任をはっきりさせるため |
| 危険が分かった情報が広がる | 危険が分かった教材・回答・コツを、すぐ止められること | 誤った情報が現場で使われ続けないようにするため |
| 工場の情報を外へ出したくない | 工場のデータを、工場の中で扱えること | 機密を含む映像や資料を守るため |
| ベテランが教材を作る時間がない | 短い手間で教材を作れること（Phase 3） | 教材が増えないと、AIが案内できる根拠も増えないため |

## 3つのタブと主な利用の流れ

| タブ | 主な操作 | 大事なルール |
| --- | --- | --- |
| 教材 | 完成した教材と、制作予定の教材を同じ一覧で見る。区間を再生する | 制作予定には「見たい」「気になる」を付けられる。未完成の教材を再生できるように見せない |
| AI | カメラを向けて、文字や音声で質問する。コツを共有する | 質問かコツかをAIが判定しても、共有する前には必ず本人が確認する |
| Q&A | 設備・工程ごとに、質問と回答を確かめる | 回答待ちが一覧で分かる。担当のベテランへ依頼が届く |

| 流れ | 内容 |
| --- | --- |
| 計画して残す | 管理者が教材の候補を追加 → ベテランを担当に指定 → ベテランが撮影・編集 → 技術承認 → 作業員が学ぶ |
| その場で聞く | AIタブを開く → 対象を映して質問 → 教材と承認済みの回答から探す → 適用条件を確かめる → 必要な区間を見る |
| 回答がない | 質問と映像をQ&Aにまとめる → 担当のベテランへ依頼 → ベテランが動画で回答 → 質問者へ届く → 承認後、次の質問の根拠になる |
| 工夫を共有する | カメラに向かって説明 → AIがコツの共有と判定 → 本人が内容と共有先を確かめる → 承認後に配信 |

## 初期版（PoC）の範囲

| 前提 | 内容 |
| --- | --- |
| 対象 | 1つの工場。サーバーは工場内のPCに置く（クラウドに移す場合は東京リージョン） |
| 端末 | 作業員は会社支給の共用端末。技術承認者と特定のベテランは個人アカウントと個別の端末 |
| データ | 開発と評価は合成データで行う。開発中に外部AIへ送ってよいのは合成データだけ |
| 題材 | 機密を含まない卓上ボール盤（架空の型式） |
| 進め方 | 要求は削らず、実装の順番をPhase 1〜4に分ける |

初期版で必須にしないもの：リアルタイムの字幕、映像の常時解析、機械の自動診断や操作、複雑な技能評価、多言語、凝った映像演出。後回しにするのは高度化であり、基本の体験は削りません。

プライバシーに関する要求（録画の同意の範囲、第三者の写り込み、閲覧範囲、保持期限）は、PoCの期間は適用せず、実際の工場で実データを扱う前に判断し直します。データには閲覧範囲や保持期限の項目を持たせ、後から使えるようにしています。

## 要求を固めた進め方

1. 体験、権限、3つのタブ、入力、録画、Q&A、通知などの要求を決め、AIと一緒に企画書と要求仕様書（v0.3）にまとめました。自分が指定したこと、補足の提案、検証が必要なことを区別して書いています。
2. 実装の前に、外部のAIレビュー（Claude Opus 5.5）で企画書と要求仕様書を見直し、27件の指摘を受けました。主な指摘は、回答してよい条件がデータとして定義されていない、録画への第三者の写り込み、未承認のコツが広がる経路、ログイン方式・端末・データの保存先が決まっていない、などです。
3. 指摘ごとに採用・代わりの案・保留を決め、決定ログに残しました（[07. 設計の判断](07_decisions.md)）。
4. 決定を反映した正式要求（v0.4）を作り、受入テストと実装の段階に結び付けました。

| 段階 | 主な内容 | 完了の条件 |
| --- | --- | --- |
| Phase 1 一巡の骨格 | API契約、サーバー（権限・検索とまとめ・Q&A・承認・停止・監査）、両OSの3タブ、名前の選択とPIN、区間の再生、文字での質問、該当がないときのQ&A登録、ベテランの動画回答、承認、受信箱 | 主な受入テストが自動試験で合格。両OSのシミュレーター・エミュレーターで一巡 |
| Phase 2 現場の入力 | 自動録画、音声入力、質問とコツの判定と共有の確認、コツの投稿と承認、制作の要望、通知、通信断と再送 | 録画・判定・通知・再送の受入テストが合格 |
| Phase 3 制作と学習 | 教材を短い手間で作る機能、学習コース、似た質問、計測 | 似た質問・学習コースの受入テストが合格 |
| Phase 4 実証の準備 | 実機と工場の環境での検証、性能の測定、セキュリティの確認、プライバシー要件の再判断 | 工場での実証を始められる状態 |

現在はPhase 2までの実装を統合し、CIで検証しています。
