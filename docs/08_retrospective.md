# 08. 振り返り

[READMEへ戻る](../README.md) · 前：[07. 設計の判断](07_decisions.md)

PoC版をPhase 2まで統合した時点（2026年10月）の振り返りです。

## うまくいったこと

| こと | 内容 |
| --- | --- |
| 要求から受入テストまでを追える形にした | 要求・要件にIDを振り、受入テストと評価ケースに結び付けた。テストのコードにも要求のIDが書かれており、実装をAIエージェントに任せても「何ができれば完成か」を判断できた |
| 作る前にレビューを入れた | 企画書と要求仕様書を、実装の前に外部のAIレビューにかけ、27件の指摘ごとに採否を決めてから作り始めた。「回答してよい条件がデータとして定義されていない」問題を、コードを書く前に直せた |
| AIの安全をコードで確かめられるようにした | 引用できる区間の判定をDBのビュー1か所に集め、AIの出力を要約の後にコードで検査する形にした。評価セット30件で、期待する動作を自動で採点できる |
| 両OSの食い違いをテストで見つけられるようにした | 同じOpenAPIの契約から両OSのクライアントを生成し、回答カードの表示ルールを共通のテストデータで確かめている |

## 難しかったこと

| こと | 内容 |
| --- | --- |
| 共用端末での「誰か」の扱い | 画面に出す名前、認証した本人、端末、送信待ちの持ち主を、それぞれ分けて扱う必要があった |
| 遅れて終わる処理の組み合わせ | 録画の確定、アップロード、HTTPの応答、ワーカーの処理が、それぞれ別々に遅れて終わる。状態・再送・持ち主の境界を決めないと、重複や取り違えが起きる |
| 画面は触るまで分からない | 撮影の形は、完成した画面を触って同じ日に2回見直した。仕様書だけでは決めきれなかった |
| CIの環境 | 署名のないシミュレーターではKeychainのテストが失敗するなど、テストを弱めずに通すための設定が必要だった |

## 学んだこと

- AIに任せる判断ほど、先にコードで決められる形にする必要がある。プロンプトの指示だけでは安全を保証できない。
- 一度決めたことでも、矛盾が見つかれば記録を残して改める。決定ログがあると、なぜ変えたのかを後から説明できる。
- 合成データでの試験、DBの並行処理の試験、シミュレーターでの試験、工場での評価は、それぞれ確かめられることが違う。どこまで確かめたかを分けて伝える必要がある。

## 見つかった技術的な課題

- 質問の処理は、AIを呼んでいる間も認証のトランザクションを保持している。実際のAIの提供元に切り替える前に、長いAIの呼び出しをトランザクションの外へ出し、最後に権限と引用を確かめ直す形にする。
- 検索は、正規化した2文字の一致による暫定の方式。表記ゆれ（ひらがな、現場の呼び方）に強い日本語の検索方式を、評価セットで比べて決める。

## 次にやること

1. **技術検証**：音声入力の方式と最低OS（実機）、区間へ移動する精度、日本語の検索方式を決める。
2. **AIの評価**：実際のAI（Claude Sonnet 5.5）で評価セットの30/30を確かめ、人による忠実性の確認をする。
3. **一巡の確認**：両OSのアプリとAPIをつなぎ、撮影・アップロード・回答・承認・再利用までを実機で通す。
4. **画面とデモ**：画面の画像と、30〜60秒のデモ動画を用意する。
5. **Phase 3**：教材を短い手間で作る機能、学習コース、似た質問をつなぐ機能を作る。
6. **Phase 4**：工場での実証に向けて、性能とセキュリティを確かめ、プライバシーの要件を判断し直す。
